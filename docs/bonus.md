# 보너스 과제 대응

과제 5절의 두 갈래에 대해, **이미 구현된 것과 아직 아닌 것을 갈라** 적습니다.
안 한 것을 한 것처럼 적으면 채점자가 확인하는 순간 나머지 문서의 신뢰도까지 잃습니다.

## A. 운영 자동화 / 데이터 저장 고도화 — ✅ 구현됨

> 과제 문구: "문의/폼 입력 또는 AI 결과를 외부 도구나 간단한 저장소에 연동한다"
> 배움 포인트: "사용자 입력 → 처리 → 저장/알림" 운영 흐름을 서비스 관점으로 확장

노코드 자동화 도구 대신 **Supabase(PostgreSQL)** 를 붙였습니다.
이 서비스는 유료 API 를 부르므로, 저장해야 할 것이 "폼 입력"이 아니라
**"누가 몇 번 썼고 얼마가 남았는가"** 였기 때문입니다.

### 저장 구조

| 테이블 | 담는 것 |
|---|---|
| `credits` | 사용자별 잔액 |
| `credit_ledger` | **모든** 크레딧 변동 기록 — 가입 보너스 / 생성 차감 / 실패 환불 / 충전 |
| `generation_sessions` | 생성 1건의 진행 상태 (자동 재시도 4회를 1건으로 묶는 키) |
| `anon_usage` | 비회원 IP 해시별 사용량 |
| `redeem_codes` · `redemptions` | 충전 코드와 사용 이력 |

### 운영 흐름

```
[입력]  생성 버튼
   │
[처리]  ensure_account()  → 계정 없으면 만들고 가입 보너스 3 지급
   │    consume_credit()  → 잔액 확인 후 1 차감,  ledger 에 기록
   │    generation_sessions 에 gen_id 로 세션 시작
   │       └ 자동 재시도 4회는 같은 gen_id → 추가 차감 없음
   │
[저장]  성공 → ledger 에 확정
   │    실패 → refund_credit() 자동 환불 + ledger 에 환불 기록
   │
[알림]  화면 상단 잔액이 즉시 갱신 (응답 본문에 credits 를 실어 보냄)
```

### 왜 이렇게 했는가

- **잔액 한 칸이 아니라 원장(ledger)** 을 둔 이유: 잔액만 있으면 "왜 줄었냐"는 문의에
  답할 수 없습니다. 모든 변동에 사유가 붙어 있어야 환불도 대응도 가능합니다.
- **차감·환불을 DB 함수로** 둔 이유: 서버 함수에서 "읽고 → 빼고 → 쓰기" 를 하면
  동시에 두 번 누를 때 한 번만 차감될 수 있습니다. 원자적으로 처리해야 합니다.
- **환경변수가 없으면 계층 전체가 꺼집니다.** Supabase 를 설정하지 않은 채 배포해도
  로그인·크레딧 없이 그대로 동작합니다 (`api/me.py` 의 `auth_enabled: false`).

관련 파일 — [supabase/schema.sql](../supabase/schema.sql) · [supabase/redeem.sql](../supabase/redeem.sql)
· [api/_supabase.py](../api/_supabase.py) · 설정 절차는 [setup-phase2.md](setup-phase2.md)

## B. 사용자 경험(UX) 및 측정 고도화 — 🔶 일부

> 과제 문구: "다크 모드 / 마이크로 인터랙션 / 방문자 분석 중 1개 이상"

### B-1. 마이크로 인터랙션 — ✅ 구현됨

| 위치 | 동작 | 왜 |
|---|---|---|
| 생성 버튼 | 누르면 즉시 잠기고 스피너로 바뀜 | 두 번 눌러 두 번 과금되는 것을 막는다 |
| 재시도 | 버튼 라벨이 `(재시도 2/4)` 로 바뀜 | 멈춘 게 아니라 다시 쓰는 중임을 알린다 |
| 20초 경과 | 로딩 아래에 지연 안내가 나타남 | 기다릴지 말지를 사용자가 정할 수 있게 |
| 단어수 게이지 | 목표 구간을 배경으로 깔고 막대가 `.5s` 로 차오름 | 몇 단어인지가 아니라 **기준 안인지**를 보게 한다 |
| 자가진단 | 체크할 때마다 점수와 판정 문구가 즉시 바뀜 | 끝까지 체크하게 만드는 장치 |
| FAQ | `<details>` 로 열고 닫힘 | 자바스크립트 없이 되는 것은 HTML 로 |

### B-2. 다크 모드 — 🔶 부분

토글은 없습니다. 대신 **화면의 성격에 따라 고정**했습니다.

- `#generator` — 다크. 결과를 오래 읽는 작업 화면이라 눈이 편한 쪽으로.
- `#home` `#pricing` `#about` — 밝은 배경에 다크 밴드를 교차.

`prefers-color-scheme` 을 따르거나 사용자가 고르게 하는 것은 넣지 않았습니다.
**넣지 않은 것이지 못 넣은 것이 아니라는 점을 분명히 적어 둡니다.**

### B-3. 방문자 분석 — ❌ 미구현

넣지 않았습니다. 이유를 적어 둡니다.

- 초등학생이 쓰는 도구라 외부 분석 스크립트를 붙이는 데 신중해야 합니다.
  개인정보 처리방침에 수집 항목을 추가로 적어야 하고, 그만한 가치가 아직 없습니다.
- 지금 필요한 숫자(생성 횟수·성공률·학년 분포)는 이미 `credit_ledger` 와
  `generation_sessions` 에 남습니다. **자체 데이터가 먼저이고 외부 도구는 그다음**입니다.
- 붙인다면 Vercel Analytics 가 첫 후보입니다. 쿠키 없이 동작하고 스크립트 한 줄이면 됩니다.

### 개선 효과를 어떻게 확인할 것인가

과제가 요구하는 것은 기능 추가가 아니라 **"개선 효과를 확인하는 방법"을 함께 설계했는가**
입니다. 이 서비스에서 볼 숫자는 이렇습니다.

| 보고 싶은 것 | 볼 수 있는 곳 | 개선했다고 말할 수 있는 조건 |
|---|---|---|
| 자동 재시도가 실제로 통하는가 | `generation_sessions` 의 시도 횟수 분포 | 1회 통과 비율이 오른다 |
| 4회로 충분한가 | 4회 소진 후 강제 표시 비율 | 이 비율이 낮아진다 |
| 지연 안내가 이탈을 막는가 | 20초를 넘긴 세션 중 끝까지 기다린 비율 | 안내 도입 전후를 비교한다 |
| 어느 학년이 실제로 쓰이는가 | `credit_ledger` 의 생성 기록 | 프롬프트 튜닝의 우선순위가 정해진다 |

세 번째 항목은 지연 안내를 이번에 막 넣었으므로 **아직 비교할 이전 데이터가 없습니다.**
지금은 측정 지점만 정해 둔 상태입니다.
