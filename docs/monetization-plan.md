## 0. 요약

비회원에게 에세이 생성 **2회**를 무료로 제공하고, 소진 시 회원가입을 거쳐
크레딧을 결제하도록 하는 3단 퍼널을 도입한다.

이를 위해 현재의 "정적 프론트엔드 + 함수 1개" 구조에 **인증과 데이터베이스**가
추가된다. 기존 `service-plan.md` 8장에서 "범위에서 제외"했던 항목을 되살리는 작업이다.

## 1. 왜 지금 구조로는 불가능한가

| 필요한 것 | 현재 상태 |
|---|---|
| "이 사용자가 2회를 썼다"는 기록 | 없음 — 서버가 상태를 전혀 저장하지 않음 |
| 사용자를 식별하는 수단 | 없음 — 로그인 개념 자체가 없음 |
| 결제 여부 확인 | 없음 |

`localStorage` 에 횟수를 적는 방법은 **무의미하다.** 시크릿 창을 열거나
개발자도구에서 한 줄 지우면 초기화된다. 돈을 받는 순간부터 횟수 차감은
반드시 **서버에서** 이루어져야 한다.

### 1-1. 먼저 막아야 할 구멍

현재 `POST /api/generate` 는 **인증이 없는 무제한 OpenAI 프록시**다.
배포 주소가 알려지면 제3자가 자기 서비스의 AI 백엔드로 그대로 갖다 쓸 수 있고,
비용은 전부 운영자가 부담한다. 유료화 이전에 이것부터 닫아야 한다.

## 2. 퍼널 설계

```
[비회원 방문]
   │
   ├─ 1회차 생성 ──▶ 정상 제공
   ├─ 2회차 생성 ──▶ 정상 제공 + "무료 체험이 끝났습니다" 안내
   │
   ▼
[3회차 시도]  ──▶  카카오 로그인 모달 (필수, 우회 불가)
   │
   ▼
[카카오 로그인 완료]  ──▶  가입 보너스 3회 지급
   │
   ▼
[크레딧 결제]  ──▶  잔여 횟수만큼 생성
```

### 2-1. 비회원 2회를 세는 방법

완벽한 방법은 없다. 세 겹으로 쌓아 **비용이 새는 것을 막는 수준**을 목표로 한다.

| 층 | 수단 | 우회 난이도 | 역할 |
|---|---|---|---|
| 1 | 브라우저 `localStorage` | 매우 쉬움 | 일반 사용자용 UX |
| 2 | 서버가 IP + User-Agent 해시로 카운트 | 보통 | 실질적 방어선 |
| 3 | 전체 익명 호출량 일일 상한 | — | 최후의 비용 방어 |

2층이 핵심이다. IP를 원문으로 저장하면 개인정보에 해당하므로 **해시로 저장**하고
24시간 후 삭제한다. 공용 IP(학원·학교) 때문에 억울하게 막히는 경우가 생기므로,
IP당 한도는 2회가 아니라 **하루 10회** 정도로 느슨하게 잡고,
개인 식별은 1층에 맡기는 편이 마찰이 적다.

## 3. 과금 모델 — 크레딧(회수권) 확정

이 서비스는 **1회 생성당 실제 원가가 발생**한다. 게다가 품질 검증 재시도 때문에
1회 생성이 최대 **4번의 API 호출**로 늘어날 수 있다(`app.js` 의 `generateWithRetry`).
따라서 정액 무제한 구독은 원가가 매출을 넘길 위험이 있어 채택하지 않는다.

**결정: 크레딧(회수권) 방식.** 1 생성 = 1 크레딧.

### 3-1. 크레딧 차감 규칙

| 동작 | 차감 |
|---|---|
| 학년 1종 생성 | 1 크레딧 |
| "전체 생성"(3개 학년 일괄) | 3 크레딧 |
| 자동 재시도(최대 4회) | **추가 차감 없음** — 품질 보증은 서비스 책임 |
| 생성 실패(오류) | 차감분 환불 |

학년별 원가는 최대 9배까지 차이가 나지만(4장), 절대 금액이 워낙 작아
차등 과금은 UX 복잡도만 늘린다. **균일 1크레딧으로 간다.**

## 4. 원가 측정 결과 (실측, 2026-08-25)

모델 `gpt-5.6-luna` / effort `medium` / 학년당 2회 실측
(단가: 입력 $0.20, 출력 $1.20 per 1M tokens / 환율 1,400원 가정)

### 4-1. API 호출 1회당

| 학년 | 입력 토큰 | 출력 토큰 | (그중 추론) | 1회 호출 원가 |
|---|---|---|---|---|
| 초1-2 | 621 | 767 | 398 | 1.5원 |
| 초3-4 | 600 | 1,106 | 658 | 2.0원 |
| 초5-6 | 609 | **4,347** | **3,762** | **7.5원** |

**초5-6이 초1-2의 5배 비싸다.** 원인은 출력 토큰이 아니라 **추론 토큰**이다.
4문단 구조 + 축약형 금지 + 180~220단어라는 제약을 동시에 만족시키느라
모델이 훨씬 오래 생각한다.

### 4-2. 재시도를 반영한 1회 생성 원가

1차 시도 기준 통과율은 6건 중 5건(초5-6에서 1건 미달)이었다.

| 학년 | 평균 호출 수 | **1회 생성 원가** |
|---|---|---|
| 초1-2 | ~1.1 | **1.6원** |
| 초3-4 | ~1.1 | **2.2원** |
| 초5-6 | ~1.9 | **14.2원** |
| **평균** | | **약 6원** |

- "전체 생성"(3학년) 1건 = 약 18원
- 최악의 경우(초5-6이 4회 모두 재시도) = 30원

> 표본이 6건이므로 초5-6의 재시도율은 오차가 크다. 운영 시작 후 실사용
> 데이터로 재측정할 것. 다만 **가격 결정에는 영향이 없다** — 원가가 판매가의
> 1/10 수준이라 오차가 흡수된다.

## 5. 상품 구성 (확정안)

| 상품 | 크레딧 | 가격 | 회당 단가 | 원가 | 마진율 |
|---|---|---|---|---|---|
| **무료 체험** (비회원) | 2 | 0원 | — | 12원 | — |
| **가입 보너스** (카카오 로그인) | 3 | 0원 | — | 18원 | — |
| **라이트** | 30 | 4,900원 | 163원 | 180원 | 93% |
| **스탠다드** | 100 | 12,900원 | 129원 | 600원 | 92% |
| **프로** | 500 | 39,000원 | 78원 | 3,000원 | 89% |

*마진율은 PG 수수료 3% 차감 후 기준.*

### 왜 이 숫자인가

- **무료 2회** — 신규 방문자 1명당 최대 12원. 하루 100명이 전부 소진해도 1,200원.
  전역 일일 상한(Phase 1)으로 이 금액이 폭주하지 않도록 막는다.
- **가입 보너스 3회** — 카카오 로그인이라는 마찰을 넘게 만들 유인. 3회면
  학년 3종을 한 주제에 대해 모두 뽑아볼 수 있어 서비스 가치를 온전히 체감한다.
- **프로 500회** — 주제 DB 165개 × 3학년 = **495회**. 즉 프로 1개면
  **전체 주제를 한 번 완주**할 수 있다. 학원의 교재 제작 수요와 정확히 맞물린다.
- 원가가 판매가의 1/10 수준이므로, 가격은 원가가 아니라 **대체 비용**
  (강사가 모범답안 1건을 직접 쓰는 시간)을 기준으로 책정했다.

### 크레딧 유효기간

**무기한.** 소멸 기한을 두면 전자상거래법상 고지 의무와 환불 분쟁이 늘어난다.
원가 부담이 없으므로 유효기간 없이 가는 편이 CS 비용이 더 싸다.

## 6. 기술 스택 변경

| 계층 | 현재 | 변경 후 |
|---|---|---|
| 프론트엔드 | 바닐라 JS | 유지 (로그인·결제 UI 추가) |
| 백엔드 | `api/generate.py` 1개 | 함수 4~5개로 증가 |
| 인증 | 없음 | **Supabase Auth** |
| DB | 없음 | **Supabase (PostgreSQL)** |
| 결제 | 없음 | **토스페이먼츠** 또는 **포트원** |

### 6-1. 왜 Supabase인가

- 무료 티어로 이 규모는 충분히 커버된다
- **카카오·구글 소셜 로그인이 내장**되어 있다 (국내 사용자는 이메일+비밀번호 가입 이탈률이 높다)
- Vercel과 함께 쓰는 사례가 많아 자료가 풍부하다
- Row Level Security로 "남의 크레딧을 못 건드리게" 하는 것을 DB 레벨에서 강제할 수 있다

### 6-2. 데이터 모델

```
users            (Supabase Auth 제공)
  id, email, created_at

credits
  user_id, balance, updated_at

generations      -- 차감 이력 = 환불·CS 대응 근거
  id, user_id, topic_no, grade, cost_tokens, created_at

anon_usage       -- 비회원 카운트, 24시간 후 삭제
  ip_hash, count, date

payments
  id, user_id, order_id, amount, credits_granted, status, created_at
```

### 6-3. 서버 함수 구성

| 경로 | 역할 |
|---|---|
| `POST /api/generate` | **수정** — 인증 확인 → 잔액 확인 → 생성 → 차감 |
| `GET /api/me` | 로그인 상태·잔여 크레딧 조회 |
| `POST /api/payment/prepare` | 주문 생성 |
| `POST /api/payment/confirm` | 결제 승인 → 크레딧 지급 |
| `POST /api/payment/webhook` | 결제사 콜백 (취소·환불 반영) |

### 6-4. 차감 순서 — 반드시 지킬 것

```
1. 인증 확인
2. 잔액 확인 (부족하면 402 반환, OpenAI 호출 안 함)
3. 잔액 선차감  ← 여기서 먼저 깎는다
4. OpenAI 호출
5. 실패 시 롤백(환불)
```

3번과 4번의 순서가 뒤바뀌면 **동시에 여러 번 요청해 잔액보다 많이 쓰는 공격**이
가능하다. 차감은 DB 트랜잭션 안에서 처리한다.

## 7. 결제 대행사 선택

| 항목 | 토스페이먼츠 | 포트원(구 아임포트) | Stripe |
|---|---|---|---|
| 사업자등록 | **필수** | **필수** | 필수 |
| 국내 카드 | 전부 | 전부 | 제한적 |
| 연동 난이도 | 쉬움 | 보통 (여러 PG 통합) | 쉬움 |
| 정산 주기 | 영업일 기준 | PG사별 상이 | 주 단위 |

> ### ⚠ 선결 조건: 사업자등록
> 국내 PG사는 **사업자등록증 없이 계약이 불가능**하다. 개인 명의로는 카드 결제를
> 붙일 수 없다. 사업자등록이 없다면 결제 단계는 진행할 수 없으며, 그 경우
> 아래 8장의 대안을 검토한다.

## 8. 사업자등록이 없는 경우의 대안

| 방식 | 설명 | 한계 |
|---|---|---|
| **초대 코드제** | 결제 없이, 운영자가 발급한 코드로 크레딧 지급 | 결제 자동화 없음 (계좌이체 후 수동 발급) |
| 카카오페이 송금 링크 | 송금 확인 후 수동으로 크레딧 지급 | 수작업, 확장 불가 |
| 결제 보류 | 무료 2회 + 회원가입까지만 먼저 구축 | 매출 없음 |

수강생 대상이라 규모가 크지 않다면 **초대 코드제가 현실적**이다.
결제 시스템 없이 유료 운영이 가능하고, 나중에 사업자등록 후 PG를 붙이면 된다.

## 9. 단계별 로드맵

각 단계는 **독립적으로 배포 가능**하다. 앞 단계만 하고 멈춰도 서비스는 동작한다.

### Phase 1 — 비용 방어  ✅ 완료 (2026-08-25)
- `api/_guard.py` 신설 — 출처 검증 + IP 해시 레이트리밋 + 전역 일일 상한
- `api/generate.py` 연동, 생성 실패 시 차감분 환불
- **배포 가능한 상태**. 상세는 아래 11장.

### Phase 2 — 무료 2회 + 카카오 로그인 (2~3일)
- Supabase 프로젝트 생성, 스키마 구축
- 카카오 로그인 (필수 / 구글은 후순위)
- 비회원 2회 카운트, 소진 시 로그인 모달
- 가입 보너스 3크레딧 지급 (계정당 1회)
- 크레딧 잔액 표시·차감

### Phase 3 — 충전 코드제  ✅ 완료 (2026-08-25)
사업자등록 전이라 PG 계약이 불가능하므로 **수동 충전 경로**로 대체했다.
- `supabase/redeem.sql` — 코드 발급·사용·현황 조회
- `api/redeem.py` — 코드 등록 엔드포인트 (무차별 대입 방어 포함)
- 크레딧 부족 안내창에 상품표 · 문의처 · 코드 입력칸
- 운영 절차는 [admin-codes.md](admin-codes.md)

### Phase 3b — PG 결제 (사업자등록 후, 2~3일)
- PG사 계약 및 테스트 연동
- 결제 준비/승인/웹훅 엔드포인트 3개
- **기존 구조를 버리지 않는다** — 충전은 결국 `grant_credit()` 호출이고
  원장(`credit_ledger`)도 그대로 공유한다. 코드제는 이후 체험 코드·쿠폰으로 존속.

### Phase 4 — 운영 (1일)
- 이용약관·개인정보처리방침 (**결제 시 법적 필수**)
- 환불 규정 (전자상거래법상 고지 의무)
- 관리자용 사용량 조회

## 11. Phase 1 구현 명세 (완료)

### 11-1. 방어 3계층 — `api/_guard.py`

| 계층 | 동작 | 환경변수 | 기본값 |
|---|---|---|---|
| 출처 검증 | `Origin`(없으면 `Referer`)이 허용 목록에 없으면 **403** | `ALLOWED_ORIGINS` | 미설정 = 검사 안 함 |
| IP 시간당 | 초과 시 **429** + `Retry-After` | `RATE_LIMIT_IP_HOURLY` | 12 |
| IP 일일 | 초과 시 **429** + `Retry-After` | `RATE_LIMIT_IP_DAILY` | 30 |
| 전역 일일 | 초과 시 **503** (최종 비용 방어선) | `RATE_LIMIT_GLOBAL_DAILY` | 500 |

- 값을 `0` 으로 두면 해당 검사가 꺼진다.
- IP는 `X-Forwarded-For` 첫 항목을 쓰고, **`IP_SALT` 를 섞어 SHA-256 해시로만**
  보관한다. 원문 IP는 저장하지 않는다(개인정보 최소 수집).
- 슬라이딩 윈도우 방식. 정각 리셋이 아니라 "최근 1시간/24시간" 기준이다.

### 11-2. 차감·환불 순서

```
프롬프트 검증 → 키 설정 확인 → 출처·레이트리밋 검사(1건 선기록)
   → OpenAI 호출 → 실패 시 _fail() 이 refund() 로 선기록분 반환
```

설정 오류(키 미설정)는 사용 이력이 아니므로 레이트리밋보다 **먼저** 검사한다.

### 11-3. 알려진 한계 — Phase 2에서 해소

카운터는 **함수 인스턴스의 메모리**에 있다. 따라서:

1. Vercel이 인스턴스를 N개 띄우면 실효 상한이 N배가 된다.
2. 인스턴스가 재활용되면 카운터가 초기화된다.
3. `ALLOWED_ORIGINS` 검사는 브라우저 기준 방어다. `curl` 로 헤더를 위조하면 통과한다.

즉 Phase 1은 **정확한 과금 장치가 아니라 비용 폭주 차단 장치**다.
정확한 횟수 관리는 Phase 2에서 DB(Supabase)로 옮긴다.

### 11-4. 최종 방어선

위 한계에도 불구하고 손실 상한이 고정되는 이유는 **OpenAI 계정의 Budget limit**
때문이다. Phase 1의 상한이 모두 뚫려도 결제액은 그 한도를 넘지 않는다.
이 설정은 반드시 유지할 것.

### 11-5. 검증 결과

`_guard` 단독 테스트 7종 전부 통과 (OpenAI 호출 없이 검증):
IP별 카운터 분리 / 시간당 429 / 환불 후 재사용 / 전역 503 /
허용 도메인 통과 · Referer 대체 인정 / 타 도메인·헤더 없는 직접호출 403 /
IP 해시 저장 / 상한 0 비활성화.

실제 엔드포인트 통합 테스트에서도 한도 3회 설정 시 4번째 요청이 429로 차단됨을 확인했다.
