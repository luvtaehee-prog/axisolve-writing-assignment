# 학습 정리 — 과제 목표 6항목

과제 3절 "이 과제를 마친 후 학습자는 아래를 스스로 설명할 수 있어야 한다" 에 대한 답입니다.
일반론이 아니라 **이 저장소의 실제 파일과 줄**로 설명합니다.

---

## 1. HTML / CSS / JavaScript 는 각각 무엇을 하는가

셋은 층이 다릅니다. 한 층이 다른 층의 일을 대신하기 시작하면 그때부터 고치기 어려워집니다.

| 층 | 이 프로젝트에서의 역할 | 파일 |
|---|---|---|
| HTML | **무엇이 있는가.** 섹션 4개, 주제 사이드바 자리, 결과 패널 자리, 입력 폼 | `index.html` (467줄) |
| CSS | **어떻게 보이는가.** 색·간격·격자, 그리고 화면이 좁아졌을 때의 배치 | `styles.css` `landing.css` `legal.css` |
| JavaScript | **무엇이 일어나는가.** 클릭을 받고, 서버를 부르고, 받은 것을 HTML 로 만들어 꽂는다 | `app.js` `nav.js` `landing.js` `auth.js` |

구체적으로 이 프로젝트에서는 이렇게 나뉘어 있습니다.

- `index.html` 의 `<main class="main" id="main">` 은 **빈 껍데기**입니다. 그 안의 내용은
  전부 `app.js` 의 `renderMain()` 이 문자열로 만들어 `innerHTML` 에 넣습니다.
  주제 165개도 HTML 에 적혀 있지 않습니다 — 서버에서 받아 옵니다.
- 학년별 색(`GRADE_COLOR`)은 JavaScript 에 있습니다. 색이 데이터에 따라 달라지기 때문입니다.
  반대로 카드 사이 간격은 CSS 에만 있습니다. 데이터와 무관하기 때문입니다.
- `nav.js` 는 섹션을 **지우거나 만들지 않고** `is-active` 클래스만 붙였다 뗍니다.
  실제로 감추는 일은 CSS 가 합니다. JavaScript 가 `style.display` 를 직접 건드리면
  나중에 CSS 로는 그 값을 못 이깁니다.

## 2. 사용자 입력이 fetch 요청이 되고, 응답이 화면에 반영되는 흐름

`#generator` 에서 "이 학년 생성" 버튼을 눌렀을 때 실제로 일어나는 일입니다.

```
①  클릭            index.html 의 <button id="generate-grade-btn">
        │           app.js 가 상위 요소에 걸어 둔 클릭 위임 핸들러가 받는다
        ▼
②  상태 변경        loadingInfo[grade] = { attempt: 1, max: 4 }
        │           renderMain() → 버튼이 비활성 + 스피너로 다시 그려진다
        ▼
③  요청 조립        buildPrompt(grade, doc, keywordsText, feedback)
        │           학년별 분량 규칙 + 출력 JSON 스키마를 문자열로 붙인다
        ▼
④  fetch           await fetch("/api/generate", { method:"POST",
        │                        headers, body: JSON.stringify({...}), signal })
        │           ← 여기서 함수는 멈추지 않는다. 브라우저는 계속 반응한다
        ▼
⑤  응답 도착        res.ok 확인 → await res.json() → 코드펜스 제거 → JSON 파싱
        │           실패하면 throw. 재시도 루프가 받아 다시 ③ 으로 간다
        ▼
⑥  검증            assess(grade, parsed) — 단어·문장·문단·축약형을 센다
        │           통과하면 나가고, 미달이면 부족한 항목을 ③ 에 되먹인다 (최대 4회)
        ▼
⑦  화면 반영        doc.grades[grade] = result.data
                    saveDraft() → localStorage
                    renderMain() → 결과 패널이 다시 그려진다
```

핵심은 **④ 에서 화면이 멈추지 않는다**는 점입니다. `await` 는 이 함수만 멈추고
브라우저는 계속 돕니다. 그래서 ② 에서 "생성 중" 을 먼저 그려 두지 않으면
사용자는 눌렀는지 아닌지 알 수 없습니다. 상태를 바꾸고 → 다시 그리고 → 요청을 보내는
순서가 뒤바뀌면 안 되는 이유입니다.

## 3. Vercel Serverless Functions 와 프론트→백엔드 호출 구조

**서버리스 함수**는 상시 켜져 있는 서버가 아니라, 요청이 올 때만 깨어나 응답하고
사라지는 함수 하나입니다. Vercel 에서는 `api/` 폴더의 파일 하나가 곧 주소 하나입니다.

| 파일 | 주소 | 하는 일 |
|---|---|---|
| `api/generate.py` | `POST /api/generate` | OpenAI 호출 (AI 기능 본체) |
| `api/topics.py` | `GET /api/topics` | 기출 주제 165개 목록 |
| `api/pdf.py` | `POST /api/pdf` | 워크북 PDF 생성 |
| `api/me.py` | `GET /api/me` | 로그인 상태·잔액 |
| `api/redeem.py` | `POST /api/redeem` | 충전 코드 등록 |
| `api/_guard.py` 등 | **주소 없음** | `_` 로 시작하면 공용 모듈. `vercel.json` 의 rewrites 로 404 처리 |

Python 함수는 `class handler(BaseHTTPRequestHandler)` 를 정의하고 `do_GET` / `do_POST` 를
구현합니다. Vercel 이 요청마다 이 클래스를 깨워 해당 메서드를 부릅니다.

프론트에서 부를 때 주소가 `/api/generate` 인 것 — 도메인이 없는 것 — 이 중요합니다.
**같은 도메인이라 브라우저가 CORS 를 따지지 않고, 무엇보다 OpenAI 주소가 브라우저에
전혀 등장하지 않습니다.** 브라우저가 아는 것은 자기 서버뿐입니다.

이 구조를 로컬에서도 똑같이 재현하려고 `dev_server.py` 를 두었습니다.
같은 규칙(`api/<이름>.py` 의 `handler`)으로 라우팅하고, `_` 로 시작하는 파일과
`.vercelignore` 에 적힌 경로를 로컬에서도 404 로 막습니다.

## 4. 환경 변수로 API 키를 관리해야 하는 이유

브라우저로 내려간 것은 전부 공개된 것입니다. JavaScript 파일에 키를 적으면
개발자도구 Sources 탭에 그대로 보이고, `.env` 를 프론트에서 읽어도 결과는 같습니다.
**"난독화"는 대책이 아닙니다.**

키가 유출되면 남이 내 계정으로 API 를 호출합니다. 요금은 내 카드로 나갑니다.

그래서 이 프로젝트에서 키는 **세 곳 중 어디에도 없습니다.**

| 장소 | 키 유무 | 이유 |
|---|---|---|
| Git 저장소 | ❌ | `.gitignore` 에 `.env` `.env.local`. `.env.example` 에는 `sk-...` 자리표시자만 |
| 브라우저로 내려가는 파일 | ❌ | 프론트는 `/api/generate` 만 부른다. OpenAI 주소를 모른다 |
| API 응답 본문 | ❌ | 서버는 `{"text": "..."}` 만 돌려준다 |
| **Vercel 환경변수** | ✅ | 서버 함수가 실행될 때만 `os.environ` 으로 읽는다 |

`.env.example` 을 저장소에 두는 이유는 **필요한 키의 이름과 의미를 알려 주되 값은 주지
않기** 위해서입니다. 받아 간 사람은 `cp .env.example .env.local` 후 자기 값을 채웁니다.

만약 키가 노출되었다면 순서는 이렇습니다.
**① OpenAI 대시보드에서 즉시 폐기 → ② 새 키 발급 → ③ Vercel 환경변수 교체 후 재배포 →
④ 커밋 이력에서 제거(`git filter-repo` 등) → ⑤ 사용량 청구서 확인.**
④ 를 먼저 하면 그동안 그 키는 계속 살아 있습니다. 폐기가 언제나 먼저입니다.

## 5. 로컬 환경과 배포 환경의 차이

같아 보이지만 다릅니다. 이 프로젝트에서 실제로 어긋났던 지점들입니다.

| 항목 | 로컬 | 배포(Vercel) |
|---|---|---|
| 환경변수 | `.env.local` 파일 | Vercel Settings > Environment Variables |
| 환경변수 반영 시점 | 서버 재시작 | **재배포 시점** — 값만 바꾸고 Redeploy 안 하면 함수는 옛 값을 본다 |
| 파일 존재 여부 | 폴더에 있는 것 전부 | `.vercelignore` 에 적힌 것은 **아예 올라가지 않는다** |
| 함수 실행 시간 | 무제한 | `vercel.json` 의 `maxDuration` (생성 60초) |
| 함수 인스턴스 | 하나 | 여러 개일 수 있다 → 메모리 카운터는 그만큼 곱해진다 |
| 폰트 | 시스템에 한글 폰트가 있다 | **없다** → `api/_fonts/` 에 동봉해야 PDF 한글이 찍힌다 |

가장 흔한 사고는 **"로컬에서는 되는데 배포하면 404"** 입니다. `.vercelignore` 로 제외한
파일을 로컬에서는 읽을 수 있기 때문입니다. 그래서 `dev_server.py` 가 같은 목록을 404 로
막습니다 — 배포 전에 로컬에서 틀리게 만들어, 배포 후에 발견하지 않도록.

배포 후 문제를 고치는 흐름은 이렇습니다.

```
증상 확인 (배포 URL에서 재현)
   └→ Vercel 대시보드 > Deployments > 해당 배포 > Functions 탭에서 로그 확인
      └→ 원인이 코드면      : 고쳐서 git push → Vercel 이 자동 재배포
         원인이 환경변수면  : 값 수정 → 반드시 Redeploy
         원인이 파일 누락이면: .vercelignore 확인 → 고쳐서 push
            └→ 배포 URL에서 다시 재현 시도
```

## 6. AI 가 만든 코드에서 오류 원인을 찾고 고치는 법

AI 코딩 도구를 쓴다고 디버깅이 사라지지 않습니다. **오히려 내가 안 쓴 코드라서 더
읽어야 합니다.** 이 프로젝트에서 실제로 겪은 세 건입니다.

### 사례 1 — "생성이 전부 실패한다" (커밋 `da09e5f`)

- 증상: 어느 학년을 눌러도 생성 실패. `node --check app.js` 는 통과.
- 원인: `customNote` 라는 변수를 **선언 없이 사용**. 문법은 맞으므로 파싱은 통과하고,
  실행 시점에 `ReferenceError` 가 났습니다.
- 배운 것: 문법 검사는 이런 것을 못 잡습니다. 그래서 최소 DOM 을 흉내내 `app.js` 를
  **실제로 실행해 보는** `tools/smoke_app.js` 를 만들었습니다. 지금은 13항목을 돌립니다.

### 사례 2 — "PDF 어휘표에 한 글자만 찍힌다" (커밋 `cd6de8f`)

- 증상: Grade 5-6 워크북의 어휘표에 `perspective: 관점` 이 `p` / `e` 로 찍힘.
- 원인: 같은 필드인데 출처에 따라 형태가 달랐습니다.
  `app.js` 가 AI 에게 요구한 스키마는 `"단어: 뜻"` 이라는 **문자열**인데,
  손으로 만든 샘플 JSON 은 `["단어", "뜻"]` 이라는 **리스트**였습니다.
  렌더러가 `w[0]`, `w[1]` 로 꺼냈으므로 문자열에서는 첫 글자와 둘째 글자가 나왔습니다.
- 고친 방법: `as_pair()` / `as_triple()` 로 두 형태를 먼저 정규화한 뒤에 쓰도록 바꿨습니다.
- 배운 것: **에러 없이 조용히 틀리는 자리**가 제일 위험합니다. 문자열도 리스트도
  `[0]` 이 되기 때문에 파이썬은 아무 말도 하지 않습니다. AI 가 만든 코드에서
  "형태가 두 갈래인 데이터" 를 먼저 의심하게 됐습니다.

### 사례 3 — "로컬은 되는데 실행이 안 된다" (이번 과제에서 발견)

- 증상: README 는 `py dev_server.py` 로 실행하라는데 그 파일이 저장소에 없음.
- 원인: `.gitignore` 에 `dev_server.py` 가 들어가 있어 한 번도 커밋되지 않았습니다.
  내 PC 에는 있으니 나만 모르고 있었습니다.
- 배운 것: **`git clone` 을 새 폴더에 한 뒤 README 대로 따라 해 보는 것**이
  유일하게 확실한 검증입니다. 실제로 이번에 그렇게 해서 찾았습니다.

### 오류를 만났을 때의 순서

1. **증상을 한 문장으로 적는다.** "안 된다" 가 아니라 "Grade 5-6 만 어휘표 첫 글자만 나온다".
2. **어느 층인지 가른다.** 개발자도구 Network 탭에서 요청이 나갔는지 → 상태 코드가 몇인지.
   요청이 안 나갔으면 JS, 4xx/5xx 면 서버, 200 인데 화면이 이상하면 렌더링입니다.
3. **서버 로그를 본다.** 로컬은 콘솔, 배포는 Vercel 의 Functions 로그.
4. **가장 작은 재현을 만든다.** `curl` 한 줄로 재현되면 브라우저 변수를 다 지운 것입니다.
5. **고친 뒤 회귀 테스트를 돌린다.** `node tools/smoke_app.js`.

AI 에게 물을 때도 "고쳐 줘" 보다 **"이 증상, 이 코드, 이 로그 — 원인 후보를 대라"** 가
훨씬 잘 듣습니다. 원인을 내가 고르면 고치는 것은 쉽습니다.
